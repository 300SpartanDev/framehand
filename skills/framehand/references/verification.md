# Verification and rework

Machines answer measurable questions: does the file decode completely, is the frame count right, are duration and aspect correct, does seeking to the same moment give the same result, are fonts or assets missing. Framing checks cover key text, the caption zone and where actions land; where there is no automatic detector, name the time windows checked by hand instead of claiming everything was checked.

An independent reviewer gets only the original request, the final MP4, the confirmed direction, the treatment (treatment.md), a source table for on-screen text (which screenshot or page each caption or UI string comes from) and the facts that must be verified; they do not read the maker's explanation first. Without the source table, a reviewer will mistake a sentence quoted from the website for "invented copy". The review must include the question "where does attention start to drift, where does it go flat?": a review that only asks right or wrong will not catch "boring", which is what users reject most often. The report gives specific timecodes, the fault, its severity, viewing coverage and limits, tied to the final file's SHA. Tell apart: not explained clearly, logic error, text unreadable, rough craft, monotonous or out-of-control rhythm, unmotivated camera move, technical fault. Following visual-direction.md, check still-frame craft and continuous motion separately; point to which detail does not survive a close look and which stretch does not advance information.

Reviewing is not about chasing a high score. Fix what blocks understanding and use, and verify the original fault and its neighbouring seams. Do not reopen trade-offs the user accepted without new evidence; when the user clearly asks to stop, wrap up as asked and state the limits of verification.

For the chosen version, save the code, timeline, asset references, sound and the identity of the finished file. Rework starts from the last version actually delivered and takes stock of earlier patches. After export, check that the target window changed as expected and the other windows did not change unexpectedly; treat encoding differences and content differences separately.

Having checked only screenshots, do not claim motion was reviewed; having run only audio metrics, do not claim it was listened to; having run only a spec conversion, do not claim a new topic passed as a finished film. Make sure the test tools catch deliberately broken input, so that "all green" does not come from checks that never ran.

Record engineering acceptance and creative acceptance separately. Frame-identical output only proves the boundary of a change or determinism, and a test count only says those counter-examples are covered; neither proves it looks good. A sample the user clearly rejected must be downgraded to a technical regression case, noting which dimension was rejected. After changing the skill, only a real production by an independent agent on an unfamiliar topic counts as a transfer trial; the author simulating two answers in the same context does not count.
